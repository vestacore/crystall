## 1. Core Architectural Vectors

Think of the system as living in a space spanned by a few orthogonal vectors. Each vector has its own hard boundaries and degrees of freedom.

### 1.1 Phase Vector (Semantic Spiral Phases)

**Axis:** `Learn → Understand → Connection → Service → Knowledge → Evolution → Responsibility`

* Each phase is a **semantic position** in the spiral, not just a step in a pipeline.
* Every phase:

  * Reads from a shared **state**.
  * Emits **artifacts** (questions, summaries, connections, candidate answers, evaluations).
  * Can spawn **branches** (parallel interpretations) in later iterations.

**Hard boundaries:**

* Phases are **named and explicit**; no “hidden extra” phases smuggled into random code.
* Each invocation of the system must have:

  * A **declared phase sequence** (ScenarioConfig).
  * A clear mapping of which phases are active and in what order.
* No “magic jumps” between phases:

  * Phase transitions are explicit in the state (e.g. `state.current_phase`, phase markers in trace).

---

### 1.2 Role Vector (cunit / punit / funit)

**Axis:** `CUNIT (space) – PUNIT (intent/questions) – FUNIT (action)`

For each phase, we conceptually have up to three roles:

* **cunit** — configures *semantic space*:

  * conceptual frames, constraints, tone, views.
* **punit** — configures *semantic intention*:

  * explicit questions, priorities, ordering.
* **funit** — executes *semantic action*:

  * calls model(s), tools, RAG, produces artifacts.

**Hard boundaries:**

* Roles are **not merged implicitly**:

  * If we skip punit in some phase, this is **explicit** in config (e.g. `punit: disabled`), not “forgotten”.
* A PromptUnit always has exactly **one** role: CUNIT *or* PUNIT *or* FUNIT.
* A phase can run 1–3 roles, but the **order is fixed**: `cunit → punit → funit` (with explicit no-op allowed).
* Business logic must not put “punit-like” behavior into a funit prompt “because it’s easier”.

---

### 1.3 Scenario Vector (Domain / Use-case Profiles)

**Axis:** Scenarios (e.g. `generic_qa`, `regtech_qa`, `doc_reading`, …)

* A **ScenarioConfig** defines:

  * Active phases and order.
  * For each phase:

    * whether branching is allowed,
    * maximum number of branches,
    * which evaluators to apply.
* Scenarios parameterize **which PromptUnits** can be used (via `scenario` field in prompts repository).

**Hard boundaries:**

* The engine is **scenario-driven**, not ad-hoc:

  * You don’t create custom pipelines in code per project; you define a scenario.
* ScenarioConfig is **data, not code**:

  * stored in YAML/JSON/etc. and loaded by the engine.
* A scenario must always specify:

  * phase list,
  * default prompt selection strategy (e.g. by `scenario + phase + role`).

---

### 1.4 Prompt/Policy Vector

**Axis:** structured storage of PromptUnits

Each **PromptUnit** has:

* `id`
* `phase`
* `role` (CUNIT/PUNIT/FUNIT)
* `scenario`
* `tags` (e.g. `["conceptual_frames", "ethics", "doc_reading"]`)
* `template`
* (optional) `priority`, `description`, schemas.

**Hard boundaries:**

* **No hardcoded prompts** inside business logic:

  * All prompts live in the prompts repository.
* Prompt lookup is **mediated by metadata**:

  * At MVP: `(scenario, phase, role)` + simple priority.
  * Later: can add embeddings, tags, descriptions.
* Changes to prompts are **configuration-level**, not code-level:

  * This preserves the architecture under evolving semantics.

---

### 1.5 State Vector (Conversation / Process State)

**Axis:** structured state shared across phases

State minimally includes:

* `user_input` (original query, metadata)
* `phases`:

  * `learn.*`, `understand.*`, etc. (per-phase artifacts)
* `sql.questions`:

  * structured question graph generated by punit roles
* `branches`:

  * per-branch sub-state and draft answers
* `trace` (RIT):

  * history of phase/role executions with inputs/outputs (summarized)
* `final_answer`:

  * the final responsibility output.

**Hard boundaries:**

* State is **explicit and serializable** (JSON-like), not implicit local variables scattered across code.
* Every phase/role must:

  * read state only from well-defined keys,
  * write outputs to defined locations.
* No “mystical memory” inside prompts:

  * prompts should refer only to what’s in state (passed as variables), not rely on hidden context.

---

### 1.6 Branching & Integration Vector

**Axis:** single-path vs. multi-branch processing

* Early phases (Learn, Understand, Connection, Knowledge) can run in **single-branch mode** for MVP.
* Later phases (Service, Knowledge, Evolution, Responsibility) can allow **branch spawning**:

  * multiple candidate interpretations,
  * multiple candidate draft answers.

Branches are represented as:

```text
state.branches: {
  branch_id: {
    path: [phase1, phase2, ...],
    artifacts: {...},
    draft_answer: "..."
  },
  ...
}
```

**Hard boundaries:**

* Branches are **first-class**: not “just variables”.
* The system must always be able to:

  * enumerate branches,
  * summarize each branch’s path and artifacts.
* No branch gets silently discarded:

  * pruning is an explicit decision with reason (e.g. “pruned due to low relevance score”).

---

### 1.7 Evaluation & Community Vector

**Axis:** evaluative agents & aggregation logic

* Evaluators are themselves **PromptUnits** (usually `phase=RESPONSIBILITY`, `role=FUNIT`, `tags=['evaluator', ...]`).
* Each evaluator:

  * receives a candidate (or a fragment),
  * returns structured scores and comments (e.g. ethics, clarity, rigor, relevance).
* A simple aggregation function turns these into:

  * per-candidate scores,
  * possible best-candidate selection.

**Hard boundaries:**

* Evaluation prompts are **separated** from generation prompts:

  * no “self-evaluation inside the same prompt” for main answer.
* Evaluation is always:

  * **structured** (scores + comments),
  * **logged** in state (for traceability).
* The final answer is **not** just “the one with highest numeric score” in all cases:

  * the integration step is a distinct responsibility phase (even if MVP just picks top one).

## 2. Hard Boundaries (Global Constraints)

Beyond per-vector boundaries, the system as a whole has some global rails:

1. **Model-agnostic core**

   * Execution engine does not assume a specific LLM; the “call model” step is injected (adapter).
   * No vendor-specific hacks baked into core architecture.

2. **Prompt visibility and control**

   * All prompts configurable in prompts repository; no hidden system prompts in code.
   * For auditing/debugging, one can always reconstruct:
     `phase → role → PromptUnit → concrete prompt text used`.

3. **Deterministic control flow (at the architecture level)**

   * The graph of possible transitions (phases, roles, branching points) is **static per scenario**.
   * Variability lives inside:

     * Choice of PromptUnits from prompts repository,
     * Outputs of the model,
     * Evaluation decisions,
       not in “random extra steps” dynamically added by business code.

4. **Traceability & introspection**

   * Every phase/role execution is logged to trace with:

     * PromptUnit id,
     * inputs summary,
     * outputs summary.
   * For any final answer we can reconstruct “how we got here” at semantic level.

5. **Human override & observability** (even if not fully implemented at MVP):

   * Design assumes that later:

     * a human can inspect branches,
     * override evaluator decisions,
     * fix or regenerate specific phases without rerunning everything.

## 3. Question Vector Map (Current Answers That Shape the Space)

Here’s a “fixed map” of key questions and the answers we **commit to for now**. These answers define the direction and density of the first algorithm sketches, but remain extendable.

### 3.1 Table of key design questions

| Question vector                                                      | Current answer (design choice)                                                                                       | Fix level |
| -------------------------------------------------------------------- |----------------------------------------------------------------------------------------------------------------------| --------- |
| Q1: Where do prompts live?                                           | All prompts live in a repository of PromptUnits (`phase`, `role`, `scenario`, `tags`, `template`).                   | Hard      |
| Q2: How are prompts selected?                                        | MVP: deterministic filter on `(scenario, phase, role)` + `priority`. Later: embeddings & tag-based selection.        | Medium    |
| Q3: How are cunit/punit/funit separated?                             | Each PromptUnit has exactly **one** role; code never inlines logic of one role into another.                         | Hard      |
| Q4: What is the phase sequence?                                      | Per scenario; strongly ordered list defined in **ScenarioConfig**. No silent phase insertion.                        | Hard      |
| Q5: How are branches represented?                                    | As explicit objects under `state.branches[branch_id]` with path + artifacts + draft_answer.                          | Hard      |
| Q6: Where do model outputs go?                                       | All outputs go into the **state** object under phase/role-specific keys + trace; no hidden side channels.            | Hard      |
| Q7: How do we generate and manage questions?                         | Questions are produced by **punit** roles and stored in `state.sql.questions` as a question graph.                   | Hard      |
| Q8: How does evaluation work?                                        | Evaluators are PromptUnits (`RESPONSIBILITY/FUNIT`) returning structured scores + comments; aggregated separately.   | Medium    |
| Q9: How is the final answer assembled?                               | MVP: select best candidate by aggregated score, then pass it through Responsibility/funit for final polishing.       | Soft→Med  |
| Q10: Do we support fragment-level merging between branches?          | Not in MVP: we plan for it, but first version uses whole-candidate selection only.                                   | Soft      |
| Q11: How do we ensure traceability?                                  | Every phase/role execution is recorded in `state.trace` with prompt id + summaries of in/out.                        | Hard      |
| Q12: How do we keep the system adaptable across domains?             | Scenarios + tags in strage; core engine is domain-agnostic, domains live in configs & prompt sets.                   | Hard      |
| Q13: How tightly do we couple to any specific LLM / provider?        | Loosely; model calls go through an adapter; core doesn’t depend on model idiosyncrasies.                             | Hard      |
| Q14: How do we handle missing/ambiguous PromptUnits in a phase/role? | MVP: fail loudly (configuration error) or fallback to default generic PromptUnit; never silently skip roles.         | Hard      |
| Q15: How do we constrain complexity in the first implementation?     | Start with single-branch path and evaluation-only Responsibility; branching & fragment merging are second iteration. | Medium    |

### 3.2 How this shapes the initial algorithm

Given these answers, the **first algorithmic sketches** are constrained to:

1. **A deterministic skeleton:**

   * Load ScenarioConfig → get phase list.
   * For each phase:

     * run CUNIT (if available),
     * run PUNIT (if available),
     * run FUNIT (if available),
   * Keep all inputs/outputs in `state`.

2. **Simple prompt selection:**

   * For `(scenario, phase, role)`, pick:

     * the PromptUnit with highest priority,
     * or the only one defined.

3. **Single-branch by default:**

   * `state.branches` may exist but initially contains at most one branch:

     * `main` or `default`.
   * Branching codepaths are present architecturally, but used minimally.

4. **Responsibility as “finalization + evaluation”:**

   * Responsibility-phase evaluators score any candidates (even if only one).
   * Responsibility/funit produces:

     * final answer text,
     * brief explanation of confidence/limitations (if desired).

5. **Every step visible and replaceable:**

   * Because prompts come from repository and state is explicit:

     * We can later swap any PromptUnit,
     * Insert new phases/branches,
     * Replace evaluation policy,
       without changing the core engine.

## 4. Variability vs. Direction & Density

* **Variability** is kept in:

  * the specific PromptUnits used per phase/role,
  * the ability to add new scenarios,
  * the option to enable branching and complex evaluation later.

* **Direction** is controlled by:

  * fixed phase sequence,
  * fixed role semantics (c/p/f),
  * consistent use of question graph (`sql.questions`),
  * clear definition of Responsibility as final integrator.

* **Density** of the algorithm’s “semantic structure” is controlled by:

  * how many roles we actually use per phase,
  * which phases are activated in each scenario,
  * how much we log to trace and question graph.

So the first implementation will look like a **clean, thin skeleton with strong bones**:

* The spiral is already there as phases.
* The micro-spiral (cunit/punit/funit) is already there as roles.
* The prompts repository, state, and evaluation are minimal but correctly placed.
* And all further complexity will only add detail **along these vectors**, not break them.
